R2-01 · Chat cards are assembled by string interpolation, so a quote in a document name breaks them

AbilityModel.ts:79, 109 · generalAbility.ts:67 · performAttack.ts:113

Resolved

Resolved 29 August 2026. The six card-marker sites now build their element with document.createElement and setAttribute through a shared buildAbilityCardContent helper, and hand over its outerHTML, so escaping is not something a future template can forget. The description below is kept as the record of the defect.

Every ability test, spend, push and attack built its chat message as a template string and drops the document name straight into an HTML attribute: ${constants.htmlDataName}="${this.parent.name}". Nothing escapes it. The reader side is fine — installAbilityCardChatWrangler pulls the values back out with getAttribute and hands them to React — but by then the damage is done in the markup.

Impact: an item called Colt "Peacemaker" produces data-name="Colt ", so the chat card shows a truncated name. Double quotes in weapon and ability names are ordinary, not exotic. The same hole accepts attribute injection: a name of x" onmouseover="alert(1) puts a live event handler on an element in every recipient's chat log.

The getTranslated path has the same shape, but not the same fix: it is split out as R2-11 and remains open.

Verified by execution The four cases were run through a DOM parser using the real template from testAbility. Peacemaker and Bob's Gun survive intact; Colt "Peacemaker" parses as "Colt "; and the injection case yields both data-name="x" and a real onmouseover attribute on the element.

Severity rationale Not rated higher, because it is not a new privilege boundary: Foundry treats chat content as trusted HTML and does not sanitise it (chat-message.mjs:414), and a player can already call ChatMessage.create with arbitrary content from their own console. The realistic damage is the broken card, which needs no attacker at all — only a double quote in a weapon name.

Fix applied: buildAbilityCardContent.ts takes a record of attribute name to value and sets each through the DOM; nullish values become empty attributes, which is what installAbilityCardChatWrangler already expects for "not applicable". Two latent bugs went with it: the Moribund World attributes were emitted unquoted (data-mw-difficulty = ${difficulty}), and data-mw-re-roll emitted a literal "" for the null case, which the reader tested for truthiness and turned into NaN. Covered by a build-then-parse test that round-trips a name containing a double quote and an injected <img>; the test was checked against the old interpolating implementation and fails there.

R2-02 · Ordered-record helpers silently break on integer-like IDs

utilities.ts:243–279 · utilities.ts:150–172 · store.ts:65–130

Medium

Equipment categories, equipment fields and PC/NPC stats are stored as objects keyed by ID, and their display order is the object's key order. moveKeyUp, moveKeyDown and renameProperty therefore rebuild the object through Object.entries and Object.fromEntries. That contract holds only while every key is non-integer-like: JavaScript orders integer-like keys first and numerically, regardless of insertion order.

All three ID sets are free text in the settings dialog (changeCategoryId, changeFieldId, setStatId), so a user can name a category 1 or a stat 10 without any warning.

Impact: the move-up/move-down buttons become silent no-ops for the affected rows, and a rename can jump a row to the top of the list. Nothing errors and nothing is lost — the UI just stops obeying. renameProperty carries a doc comment promising it "keeps the renamed key in the same relative order", which is exactly what stops being true.

Verified by execution With { "10": …, "2": …, "gear": … }, the object's own key order is already ["2", "10", "gear"]; moveKeyUp(obj, "2") returns the identical order (a no-op), and renameProperty("gear", "1", obj) returns ["1", "2", "10"] — the renamed key has moved from last to first. The same rename on non-numeric keys behaves correctly.

Fix: the cheap containment is to reject integer-like IDs where they are entered, alongside the existing duplicate-ID check in assertUniqueIds — one guard, three call sites, and the invariant becomes stated rather than assumed. The thorough fix is to stop encoding order in key order and carry an explicit ordered array of IDs, which also removes the reason renameProperty exists.

R2-03 · Dismissing the personal-detail dialog leaves the handler waiting forever

installPersonalDetailHookHandler.ts:44–81

Medium

askUserAboutAddingOrReplacing wraps a DialogV2 in a hand-rolled promise that is resolved only from the two button callbacks. Closing the dialog with the window's X or with Escape runs neither, so the promise never settles and the await in doPersonalDetailStuff never returns.

Impact: the item has already been created by this point — the hook is preCreateItem but the work is fired off with void, so creation does not wait. A user who dismisses the dialog therefore gets the new personal detail added silently alongside the existing one, never sees the follow-up "add all items from pack?" prompt, and gets no indication that anything was skipped. The pending promise and its dialog closure leak for the rest of the session.

The stray return false; at line 80, inside a Promise executor where it means nothing, is a fossil of when this ran synchronously in preCreateItem and cancelled creation by returning false. That is worth knowing before changing the flow.

Fix: use DialogV2.wait(), which resolves on close and supports rejectClose, instead of wiring the promise by hand; treat dismissal as "add" (the current default button) or as an explicit cancel. While there, decide whether creation should actually block on the answer — the current ordering is load-bearing and undocumented.

R2-04 · The party sheet writes from a broadcast hook without checking who caused it

PartySheet.tsx:48–56

Medium

deleteActor fires on every connected client. The party sheet's handler responds by writing the filtered actor list back to the party actor, with no check on which user performed the deletion — even though the handler receives userId and the parameter is sitting there with the comment // probably? next to it.

Impact: every client with the party sheet open issues the same party.update at once. The GM's write wins; the players' writes are redundant at best and rejected for lack of permission at worst, which surfaces as an error toast Foundry raises on their behalf (socket-interface.mjs:36). The more players have the sheet open, the more noise.

Consistency This is the only place in the codebase that gets it wrong. All twelve writing hook handlers under src/startup/ guard with game.userId !== userId or game.user.isActiveGM — installEquipmentCategoryHookHandler, installResourceUpdateHookHandler, installKeepTokenImageInSyncWithActor and the rest. The convention is established and followed everywhere else.

Fix: return early unless game.userId === userId. Note also that the handler shadows the outer actorIds binding with a local of the same name, which makes the write harder to read than it needs to be.

R2-05 · The validator/type parity test cannot catch the defect it was written for

validatorTypes.test-d.ts:17–54

Medium

The four Zod validators are kept in step with the published types by a type test that asserts mutual assignability: expectTypeOf<A>().toExtend<B>() in both directions. That is a deliberate, well-commented guard — and it is blind to precisely the failure it guards against.

A missing optional property passes both directions. An object without min/max still satisfies Stat, because they are optional; and Stat still satisfies the narrower shape, because it has everything that shape requires. Zod meanwhile strips whatever the schema does not declare, so the property is silently dropped on import.

Impact: HI-04 in the first review — stat bounds discarded by an export/import round trip — was exactly this, and this test was already in place and green while it happened. The next optional property added to Stat, CardCategory, PersonalDetail or EquipmentFieldMetadata will be lost the same way, just as quietly. All four validators are complete today; nothing keeps them that way.

Verified by execution The pre-HI-04 stats shape (Record<string, { name: string; default: number }>) was run against Record<string, Stat>: the mutual toExtend pair passes. Swapping one assertion to toEqualTypeOf fails it, naming min and max in the error.

Fix: replace each mutual toExtend pair with a single toEqualTypeOf. It is a smaller test that catches strictly more, and it is a one-line change per validator. Pair it with the export/import round-trip assertion the first review recommended for every validator, not just stats.

R2-06 · Equipment field defaults are skipped when the category ID does not resolve

installEquipmentCategoryHookHandler.ts:27 · equipment.ts:64

Low

The pre-create hook reads equipmentCategories[categoryId].fields with no optional chaining. categoryId comes from the incoming item and falls back to Object.keys(…)[0], so it can be a category the world no longer configures — an item imported from another world or compendium, an item whose category was since deleted or renamed, or one carrying a legacy name assigned by migrateCategoryToCategoryId. If no categories are configured at all, the fallback is undefined and the lookup fails the same way.

Impact: contained but untidy. Foundry catches exceptions thrown inside hooks (hooks.mjs:161–167), so the item is still created — just without its category's field defaults, and with a stack trace in the console the user cannot act on.

Consistency EquipmentModel.setCategoryId performs the identical lookup and guards it: settings.equipmentCategories.get()[categoryId]?.fields ?? {}. The same expression, guarded in the model and unguarded in the hook, in the same feature.

Fix: match the model's guard, and decide deliberately what an unresolvable category should mean — probably falling back to the first configured category, which is already the intent of the surrounding code.

R2-07 · assertNotNull does not check for null

utilities.ts:119–123

Low

The signature is assertNotNull<T>(t: T | undefined | null): asserts t is T, but the body only tests t === undefined and throws "t was undefined". A null passes the assertion and is then typed as T for the rest of the scope.

Impact: none today. Its two production call sites are game.user and CONFIG.Investigator, neither of which is null in practice. It is a trap rather than a bug: the name, the signature and the behaviour disagree, so the first person who reaches for it on a genuinely nullable value — combat.combatant, item.actor, styleKeyCategoryId, all of which are nullable here — gets a silent pass and a crash further down.

Fix: check == null to cover both, and take a description argument so the thrown message names what was missing.

R2-08 · AsyncTextInput and AsyncTextArea advertise an index they never pass

AsyncTextInput.tsx:6–19 · AsyncTextArea.tsx:7–17 · useAsyncUpdate.ts:34–44

Low

Both components declare onChange: (newValue: string, index?: number) => void and an index prop, and both destructure index out of props without ever using it. useAsyncUpdate types its callback as taking one argument and calls it with one, so the second parameter is always undefined.

Impact: nothing is broken now — no caller passes index, because indexed use goes through the separate IndexedAsyncTextInput and IndexedRichTextEditor. The problem is that the type says otherwise. A handler written as (value, index) => setLongNote(index, value) against this signature type-checks cleanly and writes to undefined at runtime.

Fix: drop the index prop and the second callback parameter from both components. The Indexed… variants already own that job.

R2-09 · A personal detail in an unconfigured slot throws inside the create hook

installPersonalDetailHookHandler.ts:36–40

Low

The dialog's prompt text indexes the configured slot list directly: settings.personalDetails.get()[slotIndex ?? 0].name. A personal detail whose slotIndex is beyond the current world's list — dragged in from a compendium built under a different preset, or surviving a preset change that shortened the list — makes that undefined.name.

Impact: the throw happens inside a voided async call from a hook, so it becomes an unhandled rejection: the replace-or-add dialog never appears and the user simply ends up with two details stacked in one slot, with no explanation. Shares a root with R2-03 and is worth fixing in the same pass.

R2-11 · Localized chat content interpolates names without escaping

installEquipmentAddedNotifier.ts:40 · ActiveCharacterModel.ts:87, 126

Low

Split out of R2-01, which is resolved. This half has the same cause and a different fix, so it did not travel with it. Localization#format is a plain String#replace with no escaping (localization.mjs:444), and both call sites hand it item, actor and user names to substitute into a string that becomes chat message content.

Impact: lower reach than R2-01 — these are notification messages rather than interactive cards, and the substituted value lands in text rather than inside an attribute, so a plain double quote is harmless. A name containing < still injects markup into the recipient's chat log.

Investigated and cleared

These looked like defects and are not. They are recorded with the evidence so the same reasoning does not have to be redone.

Resource sync does not loop

installResourceUpdateHookHandler writes an actor resource when an ability's pool changes, and writes the ability's pool when the resource changes. That reads like a cycle. It terminates because Foundry drops empty diffs before dispatch (client-backend.mjs:262), so the second hop is a no-op write that fires no hook. Clamping cases converge in one extra hop.

The party sheet does not re-render forever

actors is memoised on party.system.getActorIds(), and effect 2 sets state from it. If that returned a fresh array per call the pair would loop. It returns this.actorIds directly — the DataModel's own array, stable between updates — so it does not.

Journal pages survive compendium export

#onExportCompendiumPack puts document.pages, an EmbeddedCollection, through JSON.stringify. A Map subclass normally serialises to {}, which would have meant exporting journal compendia as empty shells. Foundry's Collection defines toJSON (collection.mjs:210) returning a mapped array, so the pages come through.

Fire-and-forget document writes are mostly covered

There are 131 void someDocument.update(…) call sites and none has a rejection handler. Foundry raises the notification itself for server-side failures before rejecting (socket-interface.mjs:33–37), so the user is not left blind for the common case. What stays silent is a client-side throw before dispatch — a validation error, or a bug in one of the system's own async methods. Worth knowing; not worth 131 edits.

HI-02 · Failed entity migrations are permanently marked complete

migrateWorld.ts:26–119 · migrateCompendium.ts:19–115 · migrateWorldIfNeeded.ts:56–65

Resolved

Resolved 28 August 2026. World, document, pack, and compendium-entry failures are now accumulated with an affected document UUID (where available) and rethrown as a single migration failure, so migrationFlags is only written when the whole run succeeds. Every registered migration was made idempotent first, which is what makes a retry safe: replay guards use already -migrated data, persistent per-document markers, cleared legacy source settings, or a one-shot combat-replacement marker.

Because migrations are idempotent, a retry simply re-runs the outstanding set over every document; documents that were already migrated produce an empty update and are skipped. There is therefore no per-document progress bookkeeping — just a migrationAttempts counter. Foundry retries once on the next GM startup, then stops trying automatically after the second failure, and a GM can retry by hand from GUMSHOE Settings > Misc, which also shows the last error.

Compendium lock state is restored in an awaited finally block, including when pack.migrate() or an individual entry update fails. The failure notification and error identify the affected migration targets.

Verification: focused tests cover a failed world actor migration (no completion write, error surfaced), multiple failing targets reported in one error, the automatic attempt cap, an explicit GM retry past that cap, and compendium lock restoration when either an entry update or pack.migrate() fails.
